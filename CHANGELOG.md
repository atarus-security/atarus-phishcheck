# Changelog

All notable changes to atarus-phishcheck. Dates are commit dates.

## Unreleased

### Security

`tests/test_metamorphic.py` transforms 38 base messages by each listed sender addition (empty nested multiparts, 10,001 empty parts, megabytes of white space, control characters or NULs, thousands of extra headers, a deep block before the attachment, every header duplicated, extra authentication results) and checks that, for those transforms, the score does not drop and no finding is lost. That is what the test checks, not a guarantee for every addition: other padding (markup, comments or prose before the content, many benign links before a malicious one, a second Reply-To placed first) can still lower a score (README, "Known limitations").

- **Header values were cut at 4,096 characters before any check ran, and a crafted header or MIME structure could take gigabytes of memory and minutes of CPU; every header and part is now read in full at a cost bounded inside the parser.**

  What was wrong: the standard library's default email policy parses and decodes every header it hands out, and its parser grows faster than linearly with one header's length. A 450 KB Subject made of 32,000 RFC 2047 encoded words used 7.5 GB of memory, and a 1.5 MB one was killed by the operating system. A 20 MB email of 1,257 parts with encoded words in `Content-Type` and `Content-Disposition` took 54 seconds, and attachment hashing parsed the email a second time. After parsing, every header value was cut at 4,096 characters, so 4 KB of padding in the From display name left no sender address (and with it no sender, authentication or brand check), and a long comment in Authentication-Results hid the SPF and DMARC failures written after it. An HTML body with 20,000 `<a href>` tags before one `</a>` took 28 s, because each anchor's text ran to the first `</a>`.

  What changed, in plain terms: nothing is cut before detection. Every header and every MIME part is read in full, and a file name, a sender address, a link or an authentication result is found however much padding precedes it, within the caps under "Input limits" in the README: 20 distinct file names per part, 20 mailboxes per address header and 500 distinct links per message, and passing a cap is a finding (high for file names, medium for mailboxes, low for links). Past 20,000 words and separators, the rest of one address or MIME header is read only by the lenient scan, and the header is reported as malformed. Headers no check reads are counted, not kept (the first 200 are kept); of each header a check reads, the first 1,000 are kept and all are counted. An anchor's text ends where the next anchor starts. Reports show at most 4,096 characters of a value and mark the cut; detection always reads the whole value. Each text or HTML part is still read only up to 1,000,000 characters by the content checks, but its links are taken from all of it. Attachments are hashed once, from the bytes as stored. Batch mode splits an mbox by its stored bytes instead of parsing each message in full. Measured (whole analysis, peak resident memory): a 20 MB header of encoded words 1.3 s; 20 MB of obsolete `X : v` header names 2.2 s and 0.29 GB; 10 MB of `(` in Authentication-Results 1.8 s and 0.12 GB; one part naming 300,000 files (7.5 MB) 0.2 s; a 20 MB From of 1,000,000 addresses 0.4 s; 200,000 nested anchors 0.1 s. Not bounded: the standard library parser keeps one list entry per line, so 25 MB of two-character lines in one part still peaks near 0.95 GB (README, "Input limits").

  Technically: `parser.parse_email()` takes bytes (text is encoded as UTF-8) and feeds `email.feedparser.BytesFeedParser` with the `compat32` policy, which stores raw header text and parses nothing. Headers are read with `Message.raw_items()`; `decode_words()` decodes RFC 2047 in one regex pass, `_params()` splits MIME parameters outside quotes and comments and joins RFC 2231 continuations, and addresses are read by `_address_list()` (see the address entry below). The tool never calls the library's `get_filename`, `get_param`, `decode_header` or the default policy's header parser; the parser's own boundary lookup, measured linear, is the only library parameter parsing left. The obsolete-name rewrite works in 128 KB slices, the Authentication-Results reader keeps only the outermost open comments it can report, the text digest works in slices, and file names, mailboxes and Received literals are kept in dictionaries. `read_email_file()` returns bytes; `display_copy()` cuts values for the HTML and JSON reports and the batch summary, and the terminal summary looks at no more of a value than it prints. `EmailHeaders` gained `reply_to_email` and `received_count`, and the JSON `received_count` counts every Received header, not only the first 100. Tests: `tests/test_hostile_input.py` `HeaderCostTests` (counts calls into the library header parser and requires zero), `HiddenContentTests`, `EncodedWordTests`; `tests/test_lenient_reads.py` `ScalingTests` (times every reader at n and 4n and compares peak traced memory the same way); `tests/test_additions.py` `MemoryTests` (peak traced memory under 10 bytes per input byte on nine shapes).

- **A message with very many MIME parts or very deep nesting had no bound on cost, and nesting about 1,000 levels deep crashed the run; such a message is now read in full by a linear scan and scores at least 75.**

  What was wrong: the parser had no limit on parts or nesting. It checks every line against every enclosing multipart boundary, so deep nesting over many lines grows with depth times lines (300 levels over 400,000 lines: 6 s; minutes at the 25 MiB limit). A multipart email nested about 1,000 levels deep ended the single-file run with a `RecursionError` traceback, and in batch mode the file was listed as not analyzed.

  What changed, in plain terms: past 10,000 parts, 100 levels of nesting, or nesting depth times line count over 40 million, the MIME parser stops, and what it read (top-level headers, authentication results, the parts already started) is analyzed. The limits bound cost, never what is reported: the whole message is then read again by a linear scan that does not depend on MIME structure, every check runs on what it finds as well, and nothing already found is repeated. The report says what the parser did not read and why, adds a high "MIME structure exceeds the analysis limits" finding, and scores the message at least 75 ("likely phishing"): such a structure has no ordinary use. This is an ordinary report with exit code 0. The terminal summary prints the reason, batch mode shows "analyzed with limits", and the JSON has `analysis_limited`. A CRLF counts as one line. Runs of 64 or more white space or control characters count as one character toward the content checks' share, and a blank part is never taken as the body the checks read first, so white space and control padding cannot push the real text out of the share the checks read (other padding can; see the first paragraph). Measured: the slowest raw-scan shapes (25 MB of distinct named blocks, of distinct HTML blocks, of `--x` lines) take 3.3 to 4.2 s and at most about 0.3 GB.

  Technically: `_BoundedParse` passes the parser a message factory that counts parts (`MAX_PARTS`) and reads the parser's current nesting depth (`MAX_DEPTH`, and `MAX_NESTING_WORK` for depth times lines), and on a limit returns the partial message tree from the feed parser's stack with the reason; the part walk is iterative, and a `RecursionError` is reported as a limited analysis. `analyzers/rawscan.py` finds every Content-Type, Content-Disposition and Content-Transfer-Encoding header block anywhere in the bytes, reads its file names with `parser._params` (a plain pattern past 20,000 distinct blocks), takes its body up to the next line that is `--` and a declared boundary, and decodes base64 and quoted-printable bodies; links come from the raw text, the quoted-printable reading of the whole message and every decoded block; base64 lines starting with an `MZ` or ELF header count as executable content. `rawscan.merge()` adds attachments (dangerous ones kept first, 1,000 at most), text and HTML (digests in `EmailBody.read_digests` skip what the parser read; `EmailBody.raw_scan_text` feeds the brand check) and up to 500 further links; text blocks are joined once, so the merge is linear in the number of blocks. `EmailBody.limited`, `AnalysisResult.analysis_limited`, `scoring.LIMITED_FLOOR` (75). Tests: `LimitedAnalysisTests`, `RawScanTests`, `PartLimitTests`, `MetamorphicTests`.

- **A From header the standard library could not read switched off the sender, SPF, DKIM, DMARC and brand checks; addresses are now read by the RFC 5322 grammar, leniently when needed, every reading is checked, and the recorded results never depend on From.**

  What was wrong: the sender came from `email.utils.parseaddr`, and with no sender domain the authentication check returned before reading Authentication-Results and the brand check returned at once. `Shop, The <news@shop.example.com>` (an unquoted comma), `PayPal <service@paypal.com@evil.example>`, `<service@paypal.com.@evil.example>`, `From : PayPal <service@paypal.com>` (white space before the colon, obsolete syntax the library parser skipped) and a From comment nested 2,000 levels deep all gave an empty sender, so a message the receiving server had failed on SPF and DMARC scored on its body alone. `support@paypal.com <service@evil.example>` was read as paypal.com.

  What changed, in plain terms: From, Reply-To and Return-Path are read by the RFC 5322 grammar, obsolete forms included. When that finds no address, or one other readers may see differently, a lenient reading takes the last address in angle brackets or the first address-shaped text, and every check runs on it as well. An address written as the display name in front of another is checked as a sender too. SPF, DKIM and DMARC are read from Authentication-Results whatever From holds; with no readable sender the domain the receiving server recorded (`header.from`) is used. A missing or unreadable sender is a medium finding ("No sender address could be read", "Message has no From header"), and a brand claim with no readable sender is flagged. A header name followed by white space before the colon is read as a header.

  Every header read leniently is reported, with one finding per family (address headers, header names, attachment headers, part headers), a count in the description and no header or file name in the title. A family is medium only when the strict and lenient readings disagree on a value a check uses: a different sender domain, an obsolete name on a header a check reads, or a tolerant file name that a name check flags. Otherwise it is info and adds nothing to the score. In MIME parameters, comments are dropped while splitting; any value outside the grammar (junk inside a base64 encoded word, RFC 2231 sections mixed with a plain form of the same name, a quote opening mid-word, a parameter inside a comment-like run, white space inside a quoted value such as `charset=" windows-1252"`) is reported, and a tolerant scan reads every `filename`, `name` and `charset` it can find, all of which are checked. `Shop, The <news@shop.example.com>` with `filename=Product Catalog.pdf` scores as the same message with a quoted display name and a quoted file name; ordinary messages with such shapes can score higher than before, because their sender could not be read before and the Return-Path check never ran.

  Technically: `parser._address_list()` is a linear, non-recursive tokenizer and parser (comments, quoted strings and pairs, domain literals, groups, source routes, encoded words as single words) that keeps at most 20 mailboxes and records problems; `parser.lenient_domains()` gives the other readings; `_join_obsolete_field_names()` rewrites the top header block only. `EmailHeaders` gained `malformed` (entries carry `family` and `disagree`), `sender_candidates`, `header_count` and `from_more_mailboxes`. `auth.read_authentication_details()` returns the results, the malformed note and `header_from`; `check_authentication()` no longer returns early. `brands`, the lookalike check and the homoglyph check use `sender_candidates`; the findings come from `indicators._malformed_header_findings()`. Tests: `tests/test_lenient_reads.py` `SenderFallbackTests`, `ParameterTests`; `tests/test_additions.py` `MalformedFamilyTests`; `tests/test_oracle.py` `AddressOracleTests`, `ParameterOracleTests`, which compare the sender, Reply-To, attachment names and charsets read here with what the standard library's default policy reads, on hand-written forms and about 3,800 generated variants, and require a malformed-header finding wherever they differ.

- **The receiving server's recorded From domain was never compared with the From domain read here.**

  What was wrong: `<service@paypal.com;x@evil.example>` was read as paypal.com, so the brand check took the sender as PayPal's own and the report showed the DMARC result next to paypal.com, while the receiving server had authenticated evil.example (`header.from=evil.example`).

  What changed: every `header.from` the server recorded is a sender candidate, and one that is neither the From domain read here nor a parent or child of it is a high finding ("The receiving server authenticated a different From domain"). The text after the last `@` in From (raw and with encoded words decoded) is always a sender candidate, and the other lenient readings are when From is malformed. The brand, lookalike and homoglyph checks run on every candidate. Tests: `RecordedSenderTests`, `AlignmentBoundaryTests`.

- **A sender-added DKIM signature listed first hid the failing one.**

  What was wrong: the first DKIM result won, and a sender orders its signatures. `dkim=pass header.d=attacker.example; dkim=fail header.d=supplier.example` with `dmarc=none` read as DKIM pass next to a supplier.example sender that no valid signature covered. Rewritten-From list mail with the author's broken signature listed first read as a DKIM fail.

  What changed: a DKIM pass counts only when its signing domain (`header.d`, or the domain of `header.i`) is the From domain or a parent or child of it at a label boundary (`mail.shop.example` and `shop.example`), compared in IDNA form; a sibling under a shared suffix (`evil.pages.example` for `victim.pages.example`) never counts, since without a public suffix list a shared organization cannot be told from two registrations. Otherwise a fail anywhere wins; otherwise the first result stands, and an unaligned pass is shown as "pass (not aligned with From)" with no credit (JSON: `dkim_aligned_with_from`). Rewritten-From list mail now reads DKIM pass in either order. These list messages score lower than before; that is this fix, not a lost detection. Technically: `auth.read_authentication_details()` returns every DKIM result with its domain in `dkim`; `auth.dkim_result()`; `AuthResult.dkim_shown`. Tests: `DkimAlignmentTests`.

- **Authentication-Results could be made to lose or flip a recorded result.**

  What was wrong: results were taken from the first `spf=`, `dkim=` and `dmarc=` anywhere in the header. Comment text was read as a result: `arc=none (spf=pass dkim=pass dmarc=pass); spf=fail; dkim=fail; dmarc=fail`, a CEO-fraud message the receiving server had failed on all three, was read as three passes. Property values carried results as well: `smtp.mailfrom=dmarc=pass@...`, the same in quotes, and a DKIM `header.i=spf=pass@...` each turned a fail into a pass.

  What changed, in plain terms: the header is read the way RFC 8601 defines it. Only the leading `method=result` of each `;` segment is a result, and the result must be a whole word. Comments, quoted strings and property values never count, and a backslash escapes only inside a quoted string or a comment. An unclosed comment or quote, or a backslash or `)` outside them, makes only the segment it is in unreadable: that result is unknown, never a pass, later segments are still read, and a finding says the header is malformed (high severity when an SPF, DKIM or DMARC result was lost). If openers stay unclosed after taking them literally, quotes and comments are ignored from the first remaining problem on instead of dropping the rest. A fail written at the start of an unreadable segment is still read as a fail. For SPF and DMARC, a fail in any readable segment of the header read (the first Authentication-Results header) wins, then any other result that is not a pass, then a pass, so an added pass never replaces a fail, softfail or none. The DMARC policy shown with `--online` is read from the record's `p` tag.

  Technically: `auth.read_authentication_details()` splits on `;` outside comments and quoted strings in one pass (`_segments()`); if an opener is left unclosed it runs again with those positions taken literally and marks the segments that contain them. `_METHODSPEC` reads the leading `method[/version]=result` of a segment. `_extract_dmarc_policy()` splits the tag list. Received-SPF is only shown as evidence and no result is read from it. Tests: `tests/test_hostile_input.py` `AuthResultsCommentTests`, `AuthResultsGrammarTests`; `tests/test_lenient_reads.py` `AuthGrammarTests`.

- **A domain written in Unicode and the same domain in xn-- form were compared as two domains.**

  What was wrong: `From: info@bücher.example` with Reply-To and Return-Path at `xn--bcher-kva.example`, and a link whose text and target used the two forms, raised a Reply-To mismatch, a Return-Path mismatch, a lookalike link and a link-text mismatch, so an ordinary message scored 100.

  What changed: wherever two domains are compared or deduplicated (the recorded `header.from`, sender candidates, DKIM alignment, Reply-To, Return-Path, link text against link target, lookalike links, the IDN finding), both are first put in one form: lower case, no trailing dot, IDNA labels. That message now gets only the IDN finding (see "A sender or link domain written in raw Unicode" below). Technically: `parser.canonical_domain()`. Tests: `IdnDomainTests`.

- **The HTML report carried raw escape sequences and direction overrides.**

  What was wrong: titles and evidence were HTML-escaped, but control and format characters were kept, so "Dangerous attachment type: x<U+202E>gpj.exe" displayed as "...xexe.jpg", the disguise it warns about.

  What changed: every string the HTML report and the batch summary write passes through one sanitizer, `visible_text()`, which writes control, format, surrogate, private use and unassigned characters as a visible `[U+XXXX]`; the report is built from `visible_copy()`, the rebuilt body shown in the report passes through it too, and batch report links are percent-encoded. The new technical findings (limited analysis, malformed headers, unreadable sender) have their own section in the HTML report. Tests: `ReportSanitizerTests` sets every report field to a hostile value and checks both pages.

### Fixed

- **Links in parts with an unusual Content-Transfer-Encoding, in second text and HTML parts and in HTML attachments were never read.**

  `base64 ` with a trailing space, `base64 (x)`, `"base64"` and a folded value left the part undecoded, and only the first text part and the first HTML part were read. These forms are now read before decoding (a quoted or unknown value is noted in the info "MIME part header is malformed" finding). A quoted value followed by a comment (`"base64" (x)`) is still not decoded (README, "Known limitations"). Links are read from every text and HTML part, attachments included, and the content checks (hidden text, mismatched link text, credential language) run on further parts and HTML attachments up to a shared 1,000,000-character budget. Tests: `PartDecodingTests`.

- **Executable attachments hidden by a direction override, a trailing dot, quotes or no name at all raised nothing.**

  A name with U+202E or other invisible characters, or with trailing dots or spaces (dropped by Windows), is a high finding, and names are checked as displayed: those characters and enclosing quotes are removed before the extension checks. A part counted as an attachment (an `attachment` disposition or a file name) with an executable Content-Type or an `MZ` or ELF header is a high "Executable attachment content" finding whatever its name. A part with neither a file name nor an `attachment` disposition is not checked for executable content (README, "Known limitations"). Tests: `FileNameTests`.

- **Broken or wrong input files are refused in plain words instead of crashing or scoring as quiet.**

  What was wrong: a UTF-8 byte order mark at the start of the file hid every header from the parser, so a message whose Authentication-Results said SPF, DKIM and DMARC all failed scored 0 ("no strong indicators"); a UTF-16 file did the same. An empty file, a file of blank lines and an Outlook `.msg` file all scored 0 and exited 0 as if a real email had been checked. An output path that was a file, or a directory without write permission, ended in a traceback. Batch mode exited 0 when the directory held no `.eml` files and when some files could not be analyzed.

  What changed, in plain terms: empty files and `.msg` files are refused with a one-line reason and exit code 2 (in batch mode they are skipped and listed). The `.msg` message says to save the email as `.eml` first. A leading byte order mark is removed, and UTF-16 files with a byte order mark are decoded. Input with no headers at the top gets a "Header analysis" entry under "Checks not run". An unusable output directory is reported before any analysis, with exit code 2. Batch mode exits 2 when there was nothing to analyze and 1 when at least one file was not analyzed.

  Technically: `parser.InputRejected` is the new base of `InputTooLarge` and the new `NotAnEmail`; `read_email_file()` raises `NotAnEmail` for empty and OLE compound files, re-encodes UTF-16 as UTF-8 by its byte order mark and otherwise returns the bytes without a UTF-8 byte order mark; `parse_email()` strips the same byte order marks. `EmailHeaders.header_count` records how many top-level headers were parsed. `cli.py` catches `InputRejected`, checks the output directory with `_check_output_dir()`, and sets the batch exit code from the new `skipped_out` argument of `batch.analyze_batch()`. Tests: `tests/test_hostile_input.py` `MalformedInputTests`.

- **Executable attachments were missed unless the disposition said `attachment` in lower case.**

  What was wrong: the parser treated a part as an attachment only if its Content-Disposition contained the lower-case word `attachment` and a filename. `Content-Disposition: ATTACHMENT; filename="invoice.exe"`, `inline; filename="invoice.pdf.exe"`, and a part with only `Content-Type: application/x-msdownload; name="payload.scr"` were all invisible: no dangerous-attachment or double-extension finding, no hash, and a score of 0. The hashing step used a slightly different test (case-insensitive), so the two lists could disagree.

  What changed, in plain terms: any part whose disposition is `attachment` in any case, or that names a file in Content-Disposition or Content-Type, is listed and hashed, and the attachment checks run on it. An inline text part that names a file is still read as body text. An attachment with no filename is hashed and labeled "(unnamed attachment)".

  Technically: `parser._attachment_of()` reads the disposition type and every `filename` and `name` parameter with `parser._params()`; `_extract_body()` uses it for every part and hashes each attachment, and `reputation.hash_attachments()` reads the same list. Tests: `tests/test_hostile_input.py` `AttachmentDetectionTests`.

- **Two From headers, or two mailboxes in one, went unremarked or switched the sender checks off.**

  What was wrong: a message with `From: Security <security@paypal.com>` followed by a second `From:` for the real sender was analyzed as coming from paypal.com with no finding at all, and scored 0. A single `From: security@paypal.com, x@evil-sender.test` was worse: `email.utils.parseaddr` returns nothing for two mailboxes, so the sender domain was empty and the authentication, brand and lookalike checks did not run.

  What changed: more than one From header is a high-severity finding, more than one mailbox in the From header a medium one, and the first mailbox is used as the sender so every other check still runs. The extra addresses are listed as indicators.

  Technically: `parser._address_list()` reads every mailbox; `EmailHeaders` gained `from_addresses` and `from_header_count`; the findings are raised in `indicators.extract_indicators()`. Tests: `tests/test_hostile_input.py` `SenderHeaderTests`.

- **Ordinary mail from short or two-label-suffix domains scored "suspicious" as its own lookalike; lookalikes in subdomains were missed.**

  What was wrong: the lookalike check took the last two labels as the base domain, so for `shop.co.uk` it compared the name `co`, and any link containing "co" (tesco.com, cocacola.com) was a high-severity "Lookalike domain". The same happened for one- to three-letter names such as `x.io`, which matched nextcloud.test. A plain, fully authenticated shipping notice scored 58 ("suspicious"). Separately, the ASCII lookalike check looked only at the first label, so `login.paypa1.com` was not flagged.

  What changed: common two-label public suffixes (co.uk, com.au, co.jp and similar) are recognized, names shorter than four characters are not used for substring or edit-distance matches, and the ASCII lookalike check looks at every label except the top-level one. The same name under another top-level domain (a sender at example.test linking to example.net) is still flagged, as 0.5.0 did. The shipping notice now scores 0 and `login.paypa1.com` is flagged as impersonating paypal.

  Technically: `indicators.TWO_LABEL_SUFFIXES`, `indicators.MIN_LOOKALIKE_NAME` and `_get_base_domain()`, `_is_lookalike()`; `homoglyph.check_homoglyphs()` loops over labels. This is a short list, not the Public Suffix List, to keep the project free of new dependencies. Tests: `tests/test_hostile_input.py` `LookalikeVerdictTests`.

- **One malformed URL aborted the whole analysis; upper-case, IPv6 and decimal-IP links slipped past the URL checks.**

  What was wrong: the text `http://[abc` (or `http://[zz]/`, `http://a]b/`) anywhere in a body made `urllib.parse` raise `ValueError`, which ended the run with a traceback, or in batch mode listed the email as not analyzed, so a phisher could keep a message out of a batch triage by adding eight characters. URLs were found only with a lower-case `http://` or `https://`, so `HTTP://LOGIN.PAYPA1.COM/` was never seen. The raw-IP check knew only dotted IPv4, so `http://[2001:db8::5]/`, `http://3232235777/` and `http://0x7f000001/`, which browsers open as IP addresses, scored 0. Received headers yielded IPv4 literals only, including invalid ones such as `999.1.1.1`. With `--expand-links`, a malformed Location header from a shortener raised the same `ValueError`, and a redirect to `http://2852039166/` (169.254.169.254 in decimal) was not reported as non-public.

  What changed, in plain terms: a URL with an unusable host is skipped and the rest of the email is analyzed. URL matching ignores case. IPv6 hosts and the legacy decimal, hexadecimal, octal and short IPv4 forms count as raw IP addresses, both for the body check and for redirect targets. Received headers yield validated IPv4 and IPv6 literals, up to 50 per header.

  Technically: `parser.url_hostname()` wraps `urlsplit` and is used by `indicators` and `homoglyph`; `_URL_PATTERN` is `re.IGNORECASE`; `network.host_as_ip()` parses IP literals in inet_aton style and backs `looks_like_ip()`, `public_addresses()`, `indicators._is_ip_address()` and the non-public redirect check in `urlexpand`; `urljoin` on the Location header falls back to the raw value on `ValueError`; `indicators._received_ips()` validates literals with `ipaddress`. Tests: `tests/test_hostile_input.py` `UrlHandlingTests`.

- **A sender or link domain written in raw Unicode was not treated as an IDN; five shorteners were expanded but never flagged.**

  What was wrong: the homograph check looked for the `xn--` Punycode prefix only. `service@pаypal.com` with a Cyrillic `а`, written as Unicode rather than Punycode, got no homograph finding unless the optional confusables library happened to be installed, which it is not by default. The offline shortener finding used a list of 17 hosts while `--expand-links` used 22, so links on tr.im, adf.ly, link.to, po.st and x.co were expanded online but never flagged offline.

  What changed: any non-ASCII domain in the From address or a URL is a high-severity "Non-ASCII (IDN) domain" finding that shows the Punycode form and the code points involved. Both shortener checks use the same 22-host list.

  Technically: `homoglyph.check_homoglyphs()` tests `domain.isascii()` before the Punycode check; `indicators.URL_SHORTENERS` is now `urlexpand.SHORTENER_DOMAINS`. Tests: `tests/test_hostile_input.py` `IdnAndShortenerTests`.

- **An mbox saved with a `.eml` name was read as one email without a word.**

  What was wrong: only the first message of such a file was analyzed, the others became its body text, and nothing said so. `-v/--verbose` was listed in `--help` but did nothing.

  What changed: when the input starts with an mbox `From ` line and holds more separators, "Checks not run" says roughly how many messages it holds, that only the first was analyzed, and that a `.mbox` name analyzes each one in batch mode. `-v` is still accepted but no longer shown in `--help`. Tests: `tests/test_hostile_input.py` `WrongFileTypeTests`.

- **Tests and the sample email used routable public addresses.** They now use the documentation ranges 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 and 2001:db8::/32; tests that need an address the guard accepts as public patch `ipaddress` for those ranges only, and a test checks that the documentation ranges are refused as non-public.

### Documentation

- README: new "Exit codes" and "Known limitations" sections. "Input limits" now says every header and part is read in full, lists the per-part caps, the part and nesting limits with the raw scan past them and the score floor of 75, how headers are counted and kept, measured costs and peak memory, the display cut, the refused file kinds and the byte order mark handling. The feature lists say how addresses, MIME parameters and Authentication-Results are read and when a lenient reading runs, the malformed-header families and when they score, the DKIM alignment rule, the recorded From domain check, IDN domain comparison, and the new detections (IPv6 and decimal IP links, executable content and hidden names, inline attachments, every text and HTML part scanned, raw Unicode domains, subdomain lookalikes, duplicate From headers). Batch mode says only `*.eml` at the top level of a directory is read and that an mbox needs a `.mbox` name; the scoring section lists the floor; the privacy section describes the HTML sanitizer; Testing describes the new test files.

## 0.5.0 (unreleased)

### Removed

- **The ip-api.com geolocation lookup, and with it the only plain-HTTP request the tool made.**

  What was wrong: with `--online`, up to five public IP addresses from the Received and X-Originating-IP headers were sent to ip-api.com over plain HTTP, because the free endpoint has no TLS. Anyone on the path between the analyst and that service could read which addresses were being checked, and so which email was under analysis, and could alter the answer, which fed findings such as "routed through proxy/VPN" and "geographic mismatch". The free endpoint's terms also limit it to non-commercial use, which does not fit a tool a firm runs on client mail. In return the lookup added one line of value, the country and ISP of the header addresses, which an analyst can look up themselves from the addresses the report already prints.

  What changed, in plain terms: the lookup is gone and nothing replaces it. `--online` now contacts only your DNS resolver, URLhaus and MalwareBazaar (both over HTTPS), plus the shortener hosts with `--expand-links`, so nothing the tool sends is unencrypted. The IP addresses found in the headers are still extracted and listed in every report as indicators, but they are no longer sent anywhere, and the three findings that depended on the lookup (proxy or VPN routing, hosting-provider origin, geographic mismatch with the claimed brand) no longer exist. Scores for `--online` runs can therefore come out lower than under 0.4.0 for an email that only those findings flagged. The offline "Checks not run" list no longer includes IP geolocation, and the README no longer lists ip-api.com as an open decision.

  Technically: `analyzers/geoip.py` is deleted, including its `NETWORK` declaration, `lookup_ips`, `_lookup_single_ip`, `_infer_expected_region` and `_is_received_ip`. `pipeline.py` no longer imports it or calls it, and `_lookups()` returns `["dns-spf-dmarc", "urlhaus", "malwarebazaar"]` (plus `"shortener-expansion"` with `--expand-links`), so `lookups_enabled` in the JSON and HTML output never contains `"ip-api"`. `network.Policy.destinations()` lost its ip-api.com line and now prints three lines, four with `--expand-links`. The `--online` help text, the offline notes in `batch.py`, the README (feature list, online section, "things to know" bullet, network table row, sample section, known issues) and SECURITY.md were updated to match. `requests` stays a dependency because `reputation` uses it; no dependency was added or removed. `tests/test_safe_default.py` drops the two geoip tests and gains one that the module cannot be imported and `"ip-api"` is absent from `lookups_enabled`, and one that an online run of the sample makes no GET request and still lists the header IPs as indicators. The destination-list, network-table and User-Agent tests now cover `auth`, `reputation` and `urlexpand` and assert there is no ip-api line.

### Changed

- Version is 0.5.0 in `pyproject.toml` and `atarus_phishcheck.__version__`; the User-Agent strings and the JSON `version` field follow it.

## 0.4.0 (unreleased, refresh-2026-10)

### Security

- **Offline by default, DNS included; lookups need `--online`, shortener expansion needs `--online --expand-links`.**

  What was wrong: a plain `atarus-phishcheck -i mail.eml` contacted outside hosts before anyone asked it to. It queried DNS for the sender domain's SPF and DMARC records (a query the attacker's name servers can see), posted every URL in the email, often carrying a per-recipient token, to URLhaus, sent the IPs from the headers to ip-api.com over plain HTTP, and for every shortener link sent HEAD requests that followed each Location header to any host for up to eight hops. That chain usually ends on the phisher's own server, so analyzing the email told the sender it had been opened and from which address, could burn single-use links, and for a Location of `http://10.0.0.5/` or `http://169.254.169.254/` made blind requests into the analyst's own network. `--offline` stopped the HTTP lookups but not the DNS queries, although the README said it turned every outside query off.

  What changed, in plain terms: a plain run now makes no network connection of any kind, and every report lists the checks that did not run and the flag that would enable them. Passing `--online` turns on the DNS, URLhaus, MalwareBazaar and ip-api.com lookups and prints the full list of destinations before the first one. Passing `--expand-links` as well sends one HEAD request to each shortener host and records where it redirects; the destination is never contacted, only the first hop is read, a shortener that resolves to a non-public address is refused before any request, and a redirect into a private or metadata range is reported as a high-severity finding. `--offline` is still accepted and does nothing.

  Technically: `network.Policy(online, expand_links)` is passed through `pipeline.analyze_raw()` to every analyzer; the default `OFFLINE` policy makes each of `auth.check_authentication`, `reputation.check_urls`, `reputation.check_hashes_malwarebazaar`, `geoip.lookup_ips` and `urlexpand.expand_urls` return early and append a `(check, reason)` note instead. `AnalysisResult` gained `mode`, `lookups_enabled` and `checks_not_run`, which the terminal summary, HTML report ("Checks Not Run" section and mode line) and JSON output all carry. `urlexpand` is rewritten on the standard library: `network.public_addresses()` resolves the shortener host and refuses it unless every address is global (`ipaddress`, with explicit rejection of 100.64.0.0/10, 0.0.0.0/8, IPv4-mapped, 6to4 and Teredo forms); `_head_once()` connects to that checked address with `socket.create_connection`, wraps TLS with SNI for the real host name, sends one HEAD through `http.client` and reads the Location header; nothing follows it. Each network module declares a `NETWORK` list (destination, what is sent, which flag) and the README table is written from those lists. `--expand-links` without `--online`, and `--offline` with `--online`, are usage errors (exit code 2) before any file is read. `cli.py` and `batch.py` now share one pipeline, so there is one place where a lookup can happen.

- **No false clean: verdict wording, "not listed" reputation, failed lookups recorded.**

  What was wrong: a score under 15 was labelled "clean", shown in green, and the HTML report said the email "appears legitimate based on the analysis", even in a run where no reputation or DNS check had worked. A URL that URLhaus had no record of was marked "clean". Lookups that failed for any reason were skipped silently, so a run where every lookup failed looked the same as one where every lookup passed. The missing DMARC record finding fired whenever the DNS lookup failed, which offline was always.

  What changed: the lowest verdict is `no_strong_indicators`, its text says the checks that ran found no strong indicator and that this does not establish the email is genuine, and a test forbids the words legitimate, safe and clean in verdict text, verdict names and the template. URLhaus and MalwareBazaar misses set `reputation = "not_listed"`. Every failed lookup (timeout, HTTP status, non-JSON answer, unexpected `query_status`) is recorded under checks not run with the reason. DMARC-record findings are emitted only when the lookup actually ran and answered (`AuthResult.records_looked_up`). SPF, DKIM and DMARC results default to `unknown` when the Authentication-Results header carries none, and every report states that the results are the receiving server's and that DKIM is not verified by this tool.

- **Regular expressions on email content replaced with linear scanning; input limits added.**

  What was wrong: the mismatched-link regex took 1.2 s at 12 KB and 8.9 s at 24 KB of repeated `<a href='x' ` (roughly cubic), the Reply-To address regex 3.8 s at 40 KB (quadratic), the tag-stripping regex `<[^>]+>` and the hidden-text and sanitizer regexes were quadratic on repeated unclosed tags or quotes, and the whole input file was read with no size cap. One crafted email could stall a batch run over an inbox export.

  What changed: `analyzers/htmlscan.py` (standard library) walks HTML once with `str.find` and provides `strip_tags`, `iter_tags`, `iter_anchors` (with the `</a` positions collected once and found by bisect) and `parse_attrs`; `content`, `brands` and `sanitize` use it. Address extraction uses `email.utils`. Hostnames over 253 characters are ignored. `parser.read_email_file()` refuses files over 25 MiB (exit code 2, or skipped and listed in batch mode); header values are cut at 4,096 characters, body parts at 1,000,000 characters, URLs at 2,048 characters and 500 per email, and each cut is listed under checks not run. `tests/test_safe_default.py` feeds 300 to 540 KB of each known pathological shape through the full pipeline, the sanitizer and the HTML report and requires the lot to finish in under 5 seconds (it takes about 1.5 s on a laptop).

- **Preview rebuilt from an allowlist and actually rendered; iframe fully sandboxed with a CSP.**

  What was wrong: the preview iframe showed the sanitized email as escaped source, because `html_report.py` escaped the value and Jinja's autoescape escaped it again. Had that been fixed alone, the regex sanitizer let through unquoted `src=`, `srcset`, CSS `url()`, `<base>`, `<form>` and SVG, and the iframe's `sandbox="allow-same-origin"` blocked scripts but not image or CSS loads, so opening the report would have fired the sender's tracking pixels.

  What changed: `analyzers/sanitize.py` is an allowlist tokenizer: only known tags and attributes are kept, every attribute value is re-escaped, `href` becomes `#link-blocked` with the original kept in `data-original-href` (non-web schemes are described, not copied), `src` becomes `#blocked-image`, `style` is dropped when it contains `url`, `expression`, `@`, a backslash or similar, and `<script>`, `<style>`, `<iframe>`, `<object>`, `<svg>`, `<form>`, `<base>` and friends are dropped with their content. The result is a complete document with `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'">`, embedded once-escaped in `<iframe sandbox="" referrerpolicy="no-referrer" srcdoc=...>`.

- **Terminal output: escape sequences stripped, rich markup escaped; mbox split no longer left beside the input.**

  From, Subject, finding titles and reasons are passed through `safe_output.safe_text()` (removes ANSI CSI and OSC sequences, control characters and Unicode format characters such as bidi overrides) and `rich.markup.escape()` before printing. Batch mode splits an mbox into a temporary directory under the output directory and removes it when the run ends, instead of writing `<mbox>_split/` next to the input and leaving it there; messages are capped at 10,000 per mbox.
